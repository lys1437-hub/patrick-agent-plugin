# 團隊 repo 保護指南與試行前驗收

> **狀態**：設定可用性依代管平台與方案而定（例如非公開 repo 的必要審查與 CODEOWNERS 強制，可能需要特定方案）。**套用後必須通過下方五項負例實測才算生效；沒有實測證據就標「待驗」，不寫「已有機械保證」。** 以 GitHub 為例的設定名稱以官方文件為準（查核日期 ⟨YYYY-MM-DD⟩）。

## E0 試行環境
- 只在練習 repo 試行，且執行環境中沒有 reviewer 可存取的正式機密，或已有隔離實證。
- 由團隊 admin 確認並留紀錄；不成立＝不開始試行。

## 設定（責任人：團隊 repo admin）
| 項目 | 目的 |
|---|---|
| 只能透過 PR 合併 | 擋直推主線 |
| 必要的非作者人類批准 | 對應[方法文件](README.md) §1.6 第 7 項 |
| CODEOWNERS：後端、前端兩組；跨端改動兩組各一位 | 對應 T-high 批准資格（方法文件 §1.8） |
| required checks（由 repo 技術 owner 指定） | 額度跑不動時停在待驗，不接受空綠燈 |
| 禁止 force push 與刪除主線 | 防改寫歷史 |
| 盤點誰有 bypass 權限，列名單 | 有 bypass 的人能繞過以上全部 |

## 五項負例實測（前四項要被代管平台的保護機制拒絕；第 5 項由批准者人工攔下）
| # | 操作 | 預期 | 證據 |
|---|---|---|---|
| 1 | 直推主線 | 代管平台拒絕 | 平台拒絕的輸出或畫面 |
| 2 | 缺非作者批准就合併 | 代管平台擋下合併 | 同上 |
| 3 | 缺指定檢查就合併 | 代管平台擋下合併 | 同上 |
| 4 | head 更新後沿用舊審查 | 代管平台擋下（批准撤銷或必要檢查失效） | 同上 |
| 5 | 同一個 head：舊 `PASS` 之後出現新否決 | 代管平台通常擋不住；由批准者人工撤回批准，不合併 | 批准者撤回紀錄；實測目的是證明這個人工步驟有人執行 |

- 第 1～4 項的證據必須是代管平台保護機制實際拒絕的紀錄；**操作人員自己停手不算通過**。只有第 5 項接受人工撤回的證據。
- 設定不支援或沒有測到平台阻擋：該項標「待驗」，**不開始試行**。
