# AI 協作開發工作方法：任務、審查、合併與停損

## English summary

- Purpose: a tool-agnostic method for teams where AI agents write code and documents, covering how work is isolated, reviewed, merged, and stopped when review loops stop converging.
- Topics: one task per worktree and pull request; scope declaration; evidence for every completion condition; pre-merge checks; a two-layer review gate (provisional and canonical) bound to an exact head commit; evidence receipts; dual-platform and single-platform review modes; root-cause-family counting, stop-loss thresholds, and consultation outcomes; recording rule exceptions; writing principles for rules and reports.
- License: Apache-2.0 ([LICENSE](../../LICENSE)).

## 1. 任務流程

### 1.1 一個任務＝一個 worktree＋一個分支＋一個 PR

- 從**最新的遠端主線**建立任務分支與獨立 worktree，不從本機可能落後的主線分出。
- 主線只做整合，任何 agent 都不直接在主線開發或推送。
- 不同 agent、不同任務不共用同一個 checkout。
- 只讀查詢與審查不需要另開 worktree。Reviewer 想改檔時，那個修改是**另一個任務**。

**為什麼**：隔離單位是任務，不是 agent；共用工作區的未完成工作會卡住所有人。

### 1.2 動檔前宣告 scope，交付完同一回合釋放

- 宣告內容：唯一短名、在做什麼、要動的路徑。
- 開工先看其他人的宣告；路徑重疊就先協調，不直接動。
- 看到疑似失效的宣告（很久沒動靜）：**只揭露，不替別人清**；由擁有者或決策者處理。
- 任務會改變別人依賴的共用行為（合併條件、審查放行、模型路由等）時，PR 要明列受影響的規則與行為，送審前與合併前各核一次有沒有跟主線的新改動衝突。

**為什麼**：並行工作最貴的失敗是兩邊都以為自己獨占一個路徑。

### 1.3 完成條件：每一條都是硬條件，每一條都有對應證據

- 開工時把完成條件寫成**可觀測的結果**。
- 每一條都是硬條件。可能適用、也可能不適用的驗證，要逐項寫明「列入」或「不列入」，不用「如有」「視情況」「若適用」。
- **每一條都要有對應證據**，放進交給 Reviewer 的證據裡（見 §2.5）（建議做法）：
  - 需要執行才能驗證的條件（測試、腳本比對、瀏覽器或手動實測、數字核算）：證據是可重跑的步驟與它的輸出；
  - 只看 diff 就能核對的條件（例如「版本號改成 X」）：證據就是那段 diff，一樣寫進證據裡。
- 只寫在 PR 描述或交接說明裡的「已驗證」不算證據。拿不出證據的條件：逐條列為**未驗**，寫明原因。（建議做法）

**為什麼**：Reviewer 只能核對它讀得到的東西；缺一條證據，審查就只能退回或冒充通過。

### 1.4 開 PR

PR 描述固定四個小節：**範圍**（改了什麼、刻意沒改什麼）、**完成條件對證據**（逐條，對應 §1.3）（建議做法）、**未驗項目與原因**、**審查自評**。

**審查自評**每次都要寫，決定跳過審查時也不能省略：

```text
- change_class：docs-only | behavior | tests-ci | security | data-migration | release
- evidence：實際 diff 與受影響的行為
- risk_signals：會讓失敗看起來像成功、難回復或擴大影響的訊號；沒有寫「無」
- decision：required | skip
- reason：為什麼需要或可以跳過
- base_sha／head_sha：完整 40 字元 SHA
```

**按行為判斷，不按副檔名。** 下列任一成立就是 `required`：
- 改變可執行程式、行為性設定或合併結果；
- 改測試斷言、跳過條件、CI、hook、安裝或打包；
- 涉及權限、認證、shell／Git、安全、並行或資料遷移；
- 對外發布、難回復，或錯誤容易偽裝成成功。

只有 diff 能證明不改語意、不改執行的純文字、註解或格式變動，才可以 `skip`。
`skip` 由 Author 自評**不能自己放行**：要嘛團隊事先定好「哪些路徑一律免審」的政策並機械核對，要嘛由另一個人具名背書。
免審政策至少要排除：程式碼與設定檔、會被 agent 當規則載入的檔案、skill 與流程文件本身。

Author 不合併自己的 PR；有 finding 時只由 Author 在原分支修正。

**為什麼**：`.md` 也可能是行為（規則檔、skill、流程文件會改變 agent 的行為）。

### 1.5 送審前同步主線

- 送 provisional 前、送 canonical 前，各核一次任務分支是否落後遠端主線；落後就先同步。
- 「抓取遠端」這一步失敗時，**不能**把本機舊資料的比對結果當成「已對齊」。
- 同步會改變 head，舊審查全部失效（見 §2.3），所以要在審查**之前**同步，不要在 canonical 通過後才同步。

**為什麼**：審查通過後才同步，等於要再審一次。

### 1.6 合併前核對：六項全過才合併

| # | 核對 | 不通過代表 |
|---|---|---|
| 1 | PR 目前的 head 等於審查時的 head | 審查已過期 |
| 2 | PR 開啟中、非草稿、可合併、不落後主線 | 還不能合併，先查原因 |
| 3 | 目前 head 的 required CI 全部成功 | 還沒通過機械檢查 |
| 4 | 沒有未解決的討論（讀不完整也算未通過） | 還有未處理的意見 |
| 5 | 有一筆**同一個 head** 的 canonical `PASS` 紀錄：findings 為空、base 相符、Reviewer 身分符合所用模式（§3） | 正式審查未完成 |
| 6 | 有一筆**同一個 head** 的 provisional 零 finding 紀錄，或寫明 provisional 不可用的原因 | 預審未完成或未交代 |

- **任何一項查詢失敗（逾時、格式錯、讀不到）都等於「不能合併」**，不猜測、不放行。
- 送出合併時，讓代管平台在伺服器端再核對一次 head（例如 GitHub 的 match-head-commit 參數），避免核對後、送出前被推入新內容。
- 合併指令回報失敗或逾時，**先讀回 PR 實際狀態**，不盲目重送。
- 同一個 repo 一次只合併一個 PR。已經拿到 canonical `PASS` 的 PR 優先合併，其他人先不要送新審查。
- 合併時保留遠端分支，本機刪錯才救得回來。

**為什麼**：合併是高後果、難復原的動作，每一項都要 fail-safe，不是 fail-open。

### 1.7 收尾

- 只有 PR 已合併、worktree 完全乾淨、沒有人宣告這個範圍時，才清理 worktree 與本機分支。
- 有未提交或未合併的內容，就保留 worktree 並寫交接。
- squash 合併後，`git branch -d` 能成功、`git branch --merged` 沒列出、`git cherry` 的標記，**都不能當成「可以刪」的依據**；以 PR 狀態為準。

**為什麼**：這三個指令在 squash 合併下會給出互相矛盾的答案。

## 2. 審查閘門

### 2.1 兩層：provisional 與 canonical

| | provisional（預審） | canonical（正式） |
|---|---|---|
| 目的 | 修正閉環、有界收斂 | 獨立核對語意與最終 head |
| 誰 | 全新、零繼承上下文、唯讀的 Reviewer（模型見 §3） | 同左，身分條件更嚴（見 §3） |
| 能不能放行 | **永遠不能** | 放行條件之一（還要 §1.6 其他五項） |
| 什麼時候跑 | `required` 時先跑，直到**最新 head** 零 finding | provisional 零 finding 之後 |

- provisional 不可用（額度、服務中斷）時，記錄原因後可以直接送 canonical；**較弱的閘門不能擋住較強的閘門**。
- provisional 的零 finding 結果仍是「待正式審查」，不能寫成 `PASS`、不能合併。
- 兩層都會抓程式與文件問題，不要硬切成「一邊看文件、一邊看程式」。

**為什麼**：先在便宜的一層收斂到零，再送昂貴的一層；正式那層只負責確認，不負責陪修。

### 2.2 交給 Reviewer 什麼

- **只給**：原始需求、完成條件、可重跑的 Author 驗證（證據收據）、需要特別攻擊的風險。
- **不給**：Author 的推理過程、預期的結論、舊的審查結論。
- Reviewer 不修檔。想改就停止審查，交回 Author。
- Reviewer 的原始結果**原樣**寫進 PR 留言（或無 PR 時完整交付在對話），不由 Author 摘要轉述。

**為什麼**：讀得到原始推理的 Reviewer 會被它帶著走；經 Author 轉述的結論無法稽核。

### 2.3 審查綁定 head

每筆審查紀錄至少包含：完整 base SHA、完整 head SHA、Author 與 Reviewer 的平台、Reviewer **要求的**模型與**實際取得的**模型證據、模式（provisional／canonical）、verdict、findings。

- **head 一變，舊審查立即失效**：provisional 與 canonical 同時失效。修 finding、同步主線、改一個字都算。
- 失效後要從 fresh provisional 重來，最新 head 零 finding 才能再送 canonical。
- 例外：同一個 head 的審查被中斷（工具錯誤、對話中斷），head 沒變時可以直接續跑。
- SHA 一律從指令輸出複製，不憑印象拼寫。
- 實際模型沒有證據能證實時，就記「未證實」，**不能用設定檔的預設值冒充**。

**為什麼**：審查結論只對它看過的那一份內容成立。

### 2.4 verdict、嚴重度與失敗分類

**verdict**：`PASS` 是 findings 為空陣列；有任何 actionable finding（**不論嚴重度**）就是 `CHANGES_REQUESTED`；證據不足以判斷是 `BLOCKED`，補齊 Reviewer 列出的證據後重跑，不算一次退回，也不能自行改成 `PASS`。

**嚴重度按後果分級**，先寫證據與影響，再定等級：

| 等級 | 意思 |
|---|---|
| P0 | 已造成或極可能造成不可逆資料損失、憑證外洩、正式環境大規模中斷 |
| P1 | 這個 head 會讓主要行為、安全閘門或本次發布結果錯誤，足以擋下合併 |
| P2 | 條件式或未來路徑的缺口，或局部正確性、可攜性、可靠度問題 |
| P3 | 低風險、不擋合併的具體改善。純風格不列 finding |

CI 綠燈、流程閘門、Reviewer 身分只決定能不能放行，不會自動提高 finding 等級。

**審查沒完成時**，保留原本的失敗分類，不要全部叫「額度不足」：
額度、認證、服務、逾時、輸出無效、隔離失效、來源被改、紀錄寫入失敗。

- 額度不足：不重試，不定時探測；真的要審時才試。
- 認證：由當事人自己執行官方登入，不索取、不經手任何憑證。
- 服務／逾時／不明：確認舊程序已結束後**最多重試一次**；再失敗就停。
- 隔離失效：直接停，不得降級成沒有隔離的正式審查。

**為什麼**：失敗分類決定下一步；混成一類就會用錯的方式重試。

### 2.5 證據收據

Reviewer 在隔離環境裡常常無法重跑 Author 的測試。做法是 Author 先把實跑結果存成收據，交給 Reviewer 讀：
- 收據內容：執行的指令、完整輸出、退出碼、執行時間、當時的 head、輸出內容的雜湊。
- 收據要**放到 Reviewer 讀得到的地方**交給它，不要讓 Reviewer 進 Author 的工作區去讀。
- 雜湊只是**自我一致性**核對，不是防偽簽章：有寫入權限的人一樣能做出自洽的假收據。
- 一次審查所帶的收據要涵蓋 §1.3 的每一條完成條件。（建議做法）

**為什麼**：「我跑過了，都綠」不是證據；Reviewer 自己讀到輸出才是。

### 2.6 審查期間的來源完整性

- 審查開始前與結束後，對被審的 worktree 與共用的 Git 設定各取一次指紋並比對；不一致就作廢這次審查（分類為「來源被改」）。
- 審查進行中，被審的 worktree 不動；共用同一個 Git 儲存的其他工作區，避免改共用設定、hook 等會進指紋的東西。
- 跑審查的 session 要確認沒有其他 session 正準備在同一個 Git 儲存上寫入；機械檢查看不到「停在等人回答、隨時會 commit」的 session，送審前要再問一次。（建議做法）

**為什麼**：審查期間內容被改，審到的就不是要合併的那一份。

## 3. 雙平台模式與單平台模式

> 單平台模式是團隊版政策；作者自用的 review Skill（未收進本 plugin）現行仍要求 canonical 由另一平台擔任。

團隊依自己能用的 AI 平台選一種。兩種模式的審查紀錄格式、§1.6 核對、§4 停損規則**完全相同**，差別只在 Reviewer 的身分條件。

| | 雙平台模式 | 單平台模式 |
|---|---|---|
| 適用 | 團隊能用兩個不同的 AI 平台 | 團隊只用一個 AI 平台 |
| Author | 平台 A，執行角色的模型 | 執行角色的模型 |
| provisional | 平台 A，驗收角色的模型，全新 session | 驗收角色的模型，全新 session |
| canonical | **平台 B**，驗收角色的模型，全新 session | 驗收角色的模型，**與 Author 不同的模型**，零繼承上下文、獨立啟動的全新 session |
| 紀錄要能核對 | Reviewer 平台不在 Author 平台之列 | Reviewer 模型不等於 Author 模型；Reviewer 不是從 Author 對話派出的子代理 |

### 3.1 單平台模式的條件

單平台模式下，canonical 成立要**同時**滿足：
1. **不同模型**：Reviewer 用驗收角色的模型，而且跟 Author 用的執行角色模型不同。團隊路由表若把兩個角色設成同一個模型，單平台 canonical **不成立**，要先改路由表。
2. **零繼承上下文**：Reviewer 只拿到 §2.2 的輸入，看不到 Author 的對話、推理或舊審查結論。
3. **獨立啟動的全新 session**：不是 Author 對話裡派出的子代理。子代理的結果會先經過 Author 的對話才被記錄，無法保證原樣落到 PR。
4. **實際模型有證據**：canonical 的實際模型要能由平台回傳的證據證實與 Author 不同；證實不了，這筆紀錄只能算 provisional。

同平台的子代理仍然可以做 provisional、事實核對與純機械的合併執行。

### 3.2 兩種模式共通：換模型或換平台解除不了的事

下列三種情況，**不能靠換模型、換平台或換一個 session 解除**，要先修好根本原因再重審：
- **隔離失效**：Reviewer 的唯讀或隔離邊界沒有建立起來。
- **來源被改**：審查期間被審內容或共用設定變了（§2.6）。
- **證據沒存好**：收據缺漏、讀不到或對不上 head（§2.5）。
- 另外，同平台的意見不能冒稱跨平台審查。

**為什麼**：這三種是「審到的東西不可信」，不是「審的人不夠強」。

### 3.3 雙平台團隊遇到另一平台不可用

- 另一平台額度不足或服務中斷時，provisional 可以照跑，但結果仍是「待正式審查」，不能合併。
- 要不要允許暫時改用單平台模式放行，**由團隊事先明文決定**；沒有明文決定前，等另一平台恢復，對最新 head 補正式審查。

## 4. 收斂與停損

### 4.1 為什麼要停損

審查迴圈失控的常見形狀：finding → 新增一段解釋或判讀機制 → 它變成新的交付承諾 → 下一輪發現它不成立 → 再新增解釋。停損規則在這個形狀出現時**強制停下來重新判斷**，而不是再修一輪。

### 4.2 輪次規則

**provisional**：

| 輪 | 結果 | 下一步 |
|---|---|---|
| 1 | 零 finding | 送 canonical |
| 1 | P0／P1、核心抽象被推翻、修正必須新增 owner／協定／權限邊界 | 立即 AC |
| 1 | 其他 | 有界修正（需要時先做 CC，見 §4.4），進第 2 輪 |
| 2 | 零 finding | 送 canonical |
| 2 | P0／P1、同一 invariant 再次出現 P2、兩個以上 actionable P2、需要新增 owner／協定／權限、例外分支持續增加 | 停止修補，AC |
| 2 | 未命中本輪的 AC 條件，而且只有一個可證明孤立的新 P2 或 P3 | 有界修正後進第 3 輪 |
| 2 | 未命中本輪的 AC 條件，零 P0／P1／P2、有多個 P3，而且表下三項同時成立 | 有界修正後進第 3 輪 |
| 2 | 其他 finding 組合 | 一律停止修補，AC |
| 3 | 任何 actionable finding | 停止修補，交決策者；**不自動進第 4 輪** |

第 2 輪有多個 P3 要進第 3 輪，下列三項必須**同時成立**：
1. 每個 P3 分屬不同根因家族，而且這些家族在先前輪次都沒出現過；
2. 沒有一個 P3 落在上一輪修正新增或改動的內容上（**Author 無法確定時，視為落在上面**）；
3. 修正不改變行為契約，範圍同 §4.5 provisional 退回的第 2 條。

**canonical**：
- P0／P1、核心邊界被推翻、重複 invariant、兩個以上 actionable P2、需要新增 owner／協定／權限：立即 AC。
- 單一孤立 finding：可以先做 CC，再做一次有界修正。
- 任何修正都產生新 head：先拿到 fresh provisional 零 finding，才能再送 canonical。
- **第二個 canonical head 仍被退回：不論嚴重度，停止修補，AC。**

架構方案落地後，同樣從 fresh provisional 開始。

**為什麼**：一次架構改寫後，正常情況兩輪內收斂——第一輪探邊界，第二輪確認為零。

### 4.3 根因家族計數

- 每個 finding 標一個**根因家族**，用根因描述命名（例如「外部工具輸出的解碼契約缺口」）。
- 同一個底層缺陷只是換了呼叫點、欄位或嚴重度，**仍算同一家族**。沒把握時先當成同一家族：寧可錯併，不要錯放。
- **計數單位是審查輪**：同一家族在同一輪不論出現幾處，只算 1 次。出現幾處另記為嚴重度訊號。
- 計數**不分嚴重度、不分 provisional／canonical，跨輪、跨 session、跨 lineage 都不歸零**。
- 採納了 Reviewer 的建議、事後發現建議本身錯了：**仍計入**同一家族，另標「採納了錯建議」（相對於「沒修好」）。這個標記只影響事後分析，不影響計數。
- finding 落在上一輪修正新增或改動的內容上（Author 無法確定時，視為落在上面）：照根因判斷，根因相同就計入既有家族，不因為落在新內容上而另計。

**強制門檻**：
- 同一家族的出現都在**同一個 Author session** 內：第 3 次強制 AC。
- 任兩次出現分屬**不同的 Author session**：第 2 次強制 AC。

「Author session」指實際改程式的那個工作對話。**全新啟動的對話接手就算一次交接**，不論是否沿用同一個短名；同一個對話因為上下文壓縮插入摘要，不算交接。Reviewer 與諮詢用的全新 session 不算 Author session。

這個門檻是**補充觸發**，不放寬 §4.2 任何較嚴的條件。命中門檻時，Author 給決策者的建議只能是「依規則必須做 AC」；只有 Author 明確判斷這次可能不屬於同一家族時，才能附依據請決策者覆核，不能把「先修再跑一輪」跟 AC 並列成同等選項。

**為什麼**：跨 session 復發要重建脈絡、交接文件本身也可能出錯，代價遠高於同 session 多一輪。

### 4.4 兩種諮詢：CC 與 AC

兩種諮詢都是**全新、唯讀、不是驗收**；都不產生 `PASS`，也不重置輪次。

| | CC（修正諮詢） | AC（架構諮詢） |
|---|---|---|
| 產出 | 分群 finding 的共同根因、鄰近風險、最小修正範圍、回歸對照 | 比較 2～3 個方案、推薦遷移邊界、定義驗證契約 |
| 結論 | 局部修正／有界重構／升級 AC | 三種處置之一（見下） |
| 何時做 | 高風險類別（安全、並行、I/O 生命週期、紀錄完整性）每次退回後、Author 動手前；一般變更在 P2 跨模組、兩個以上相關 finding、或修正邊界不明時 | §4.2、§4.3 觸發時 |

**AC 的三種處置**，產出要寫明依據，不能只寫「已做 AC」就結案：
1. **有界修正**：全部 finding 屬於同一種有界修法，直接修。
2. **架構層改動**：根因是設計缺陷，升級成架構改動。
3. **降範圍**：修法本身會再製造同一家族（自我指涉）。先處理可控部分，把無法收斂的部分明確移出這次範圍，不留「待補」之類跨 PR 的承諾。降範圍可以由決策者**事先概括授權**，AC 判定屬於自我指涉時直接採用。

**lineage**：只有決策者核准方案、而且架構改動實作完成後，才開始新 lineage，provisional 輪次從第 1 輪重算。**根因家族計數不重算**：架構修正後同族再出現，正是最嚴重的訊號。

**AC 之後同一家族又復發、需要再做 AC**：換一個跟前次不同的諮詢視角（雙平台模式換平台；單平台模式換一個沒處理過這個家族的模型），引用前次 AC，說明是「沒照方案做完」「前提不成立」還是「修法再生缺口」（建議做法）。AC 不設次數上限，也不因次數自動升級成其他機制。

參與過任何諮詢的 session，不能擔任同一個 PR 的驗收者。

**為什麼**：停損觸發的是「停下來重新判斷」，不是自動宣判「一定要重寫」。

### 4.5 修正核准分界：哪些修正不用等人

**provisional 退回**：以下四項**同時成立**才能直接修；缺一項就整輪交決策者核准（finding 分類、修正範圍、預估要產生幾個 head）：
1. 修正落在這個任務已核准的範圍內；
2. 不改變行為契約或安全邊界（不增減權限、不改對外發布範圍、不改資料保存或刪除規則）；
3. 修法唯一，沒有需要在多個等效方案間取捨的空間；
4. 既有測試可以直接驗證修正結果。

**canonical 退回**：第 1 次實質退回可以自動修正、產生 1 個新 head；第 2 次依 §4.2 停止並做 AC。

**諮詢結論的 head 預算**：依 CC 或 AC 推薦方案實作的第 1 個修正 head 可以自動做；之後若還要再產生新 head，整輪交決策者核准。

- 「實質退回」指有 actionable finding 的 `CHANGES_REQUESTED`；`BLOCKED` 不計。
- AC 的方案之間有實質取捨，或修正會擴張產品目標、對外權限、發布範圍：一律先問。
- 觸發 AC 或 canonical 第 2 次退回時，Author 可以附理由建議換更強的模型執行修正，由決策者決定，不自動切換。這是經驗建議，不是已驗證的因果。

**為什麼**：需要一個人判斷的，是「要不要多花一個 head」，不是「這個 finding 對不對」。

### 4.6 處置紀錄（建議做法）

觸發 CC 或 AC 後，Author 在 PR 描述記下這四段，讓任何人能從 finding 追到結果：
1. 觸發依據：命中哪一條規則，以及觸發它的審查紀錄；家族門檻觸發時，列出該家族每次出現的紀錄。
2. 處置決策：諮詢產出在哪、採用哪一種處置、誰核准（或依據哪一條免核准）。
3. 修正 head：依這個處置產生的第一個完整 head SHA。
4. 下一次有效審查：第 3 段 head 之後第一筆完成的審查紀錄。

**為什麼**：「做過 AC」「修過了」「驗過了」在摘要裡很容易混成同一件事。

### 4.7 規則例外的記錄方式

停損規則偶爾會被決策者明確豁免。例外只能由決策者核准，事先或當下皆可，而且要寫進 PR 描述（或團隊的計畫文件），至少包含：

| 欄位 | 內容 |
|---|---|
| 豁免哪一條 | 規則段落名稱 |
| 觸發事實 | 家族名稱、第幾次出現、分屬哪些 session、對應的審查紀錄 |
| 核准者與時間 | 誰、什麼時候、事先還是當下 |
| 理由 | 一兩句，寫事實不寫論證 |
| 改採的處置 | 例如「跳過這次 AC，直接做結構性收斂」「第 N 次就降範圍、不再做 AC」 |
| 適用範圍 | 只限這一次，或這個家族到第幾次為止 |
| 再犯時怎麼辦 | 例如「收斂後同一家族再出現，一律強制 AC，不得再援引本例外」 |

- 每一筆都要明寫「**這是例外，不是新慣例**」。
- 事先核准的例外要**逐字核對情境**：條文寫的是某一輪、某一種退回，就只適用那種；對不上就停下來問。（建議做法）

**為什麼**：例外沒有邊界，就會變成下一個人援引的前例。

## 5. 撰寫原則

適用於規則檔、流程文件、PR 描述、交接、審查與事故說明。

### 5.1 記事實，不記論證（建議做法）

驗收敘事、規則說明、事故說明、跨檔摘要，預設只保留：**固定版本的事實、必要的操作契約、原始證據連結、未驗範圍**。

寫之前用三個問題自檢，中越多題越容易在審查裡失控：
- (a) 同一段是否混寫了壽命不同的事實（固定時點的事實、會變的狀態、提案）？
- (b) 是否宣稱適用於未來的 head？
- (c) 是否持有另一份文件的摘要副本？

**為什麼**：每一句論證都是一個新的可被推翻的承諾；事實加連結不會。

### 5.2 會變動的值只寫指標

模型名稱、reasoning effort、數值門檻、逾時秒數、原始碼行號、由腳本判定的欄位值——這些值的正本在路由表或實作裡。規則檔只寫**指向正本的指標**，不抄寫值；規則本身仍寫在規則檔。

**為什麼**：抄一份值就多一份會過期的副本，改一邊忘另一邊。

### 5.3 別人給的措辭都當待核對草稿

- 不論措辭來自決策者、規劃 session、Reviewer 還是自己，寫進規則或文件前都先對照實作或直接證據。
- 提供措辭不等於證實能力；對不上時先揭露差異，不寫成現有能力，也不為了配合措辭去改工具。
- 描述判定邏輯時，指向函式名與測試名，不用文字重述一遍。

**為什麼**：轉述過的能力描述，是規則文件裡最常見的錯誤來源。

### 5.4 引用出處前分開查三件事

1. **檔案存在**；
2. **內容確實是那個意思**；
3. **版控位置**：已在主線、只在某個 PR 的分支，還是根本沒提交。

第 3 項最容易漏，因為前兩項成立會讓人以為「已經查過」。收到其他 session 的指示或回報時同樣要自查：head SHA、diff 範圍、出處的版控位置、檔案實際措辭跟口頭描述是否一致。**Reviewer 讀的是檔案，不是報告。**

**為什麼**：只在某個分支上的「規則」，對主線上的人來說不存在。

### 5.5 其他三條

- **假設的前提不要寫成理由**：結論對不代表理由對；理由是給下一個人推論用的，錯的理由會長期誤導。（建議做法）
- **同一段敘述分散在多處、又沒有機械同步時，改一處要找齊全部**；可以的話收斂成一處正本加指標。
- **待辦缺口不要只寫在 PR 描述**：合併後沒人會回頭看，要登記到團隊的交接或待辦清單。（建議做法）

## 7. 最小採用清單

第一次導入時，先做這五件，其餘等踩到再加（加規則前先過 TEAM_RULES「加新規則之前」的三個問題）：
1. 一個任務一個 worktree、一個 PR；動檔前宣告 scope（§1.1、§1.2）。
2. PR 描述固定四小節，完成條件逐條對證據（§1.3、§1.4）（建議做法）。
3. 選定雙平台或單平台模式，寫進規則檔（§3）。
4. 合併前六項核對，任一查不到就不合併（§1.6）。
5. finding 標根因家族並逐輪累計（§4.3）。
