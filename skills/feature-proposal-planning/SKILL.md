# 功能提案規劃

把「我想做這個功能」變成一份**能被主管拍板**的提案。

核心差別不在版面，在於：**每個設計決策都要指得出是哪一筆實測數據推出來的**，而且要主動說清楚哪些還沒被驗證。

---

## 使用時機

- 要提一個新功能 / 新活動機制，需要說服決策層投資
- 既有機制要做成效檢視（health check）或競品比較，並收斂成行動方案
- 手上已有數據分析結果，要轉成決策文件

## 不適用情境

- 只是要查數字或跑分析 → 用 `igaming-ops-analysis`
- 功能已定案、要寫開發規格 / PRD → 直接寫規格，不需要提案論證
- 要拆 story、寫 AC / DoD → 用 `anthropic-skills:ogg-*` 系列（**雇主環境專用，不在本 plugin 內**）
- 一次性的簡報排版美化

---

## 必要輸入

開始前必須確認，缺任何一項先問，不要猜：

1. **提案類型**：新功能提案 / 成效檢視 / 競品比較後的優化提案
2. **決策對象**：誰要拍板？（Leadership / PM 團隊 / 風控）決定深度與語言
3. **數據來源與期間**：哪些表、什麼區間、幣別換算基準
4. **適用範圍**：哪些品牌 × 哪些市場
5. **已有的文件資產**：Rules / PRD / EV 測算 / 參數表 / UI 稿，各到第幾版

## 判斷與工作流程

### Step 1：先跑口徑閘門

任何數字進到提案前，先過 `igaming-ops-analysis` 的口徑檢查。

**提案裡出現未經口徑確認的數字，是最嚴重的失誤** — 一旦被抓到一個數字口徑錯，整份提案的可信度歸零，而且會被要求全部重算。

### Step 2：找出「重新框定」的角度

不要照著被問的問題答。先確認**原本的問題框架有沒有問錯**。

- 問「這個功能要不要做」→ 若數據顯示現況嚴重低投入，改框成「為什麼這個管道這麼小」
- 問「成本會不會太高」→ 若成本結構上封頂，改框成「風險不在成本，在品質與套利」

框定寫成一句對照句放在該段開頭：`不是 X — 是 Y`。

### Step 3：數據洞察 → 設計決策的顯性映射

這是整份提案的骨幹。**每一條洞察必須配一條設計決策**，兩者並排寫，中間用 `→` 連接。

格式：

```
1  [實測數據 + 具體數字 + 樣本範圍]
   → [因此設計成什麼樣子，以及為什麼這個設計直接回應了上面的數據]
```

#### 證據強度要分級，不要只有「實測 vs 假設」二元

二元標記會掩蓋巨大差距——台股專案實測發現，同標「有證據」的標的裡，
最強的被提及 204 次、最弱的只有 1 次，**卻長得一模一樣**。改用四級：

| 級別 | 判準 | 可以怎麼用 |
| :-- | :-- | :-- |
| **E1** | 本專案實測，樣本充足、口徑已確認 | 可作為設計決策的直接依據 |
| **E2** | 有數據但樣本小、單一來源或口徑待確認 | **單一來源不足以支撐決策**，需第二個來源佐證 |
| **E3** | 無本專案數據，但有外部／競品／行業佐證 | 標「方向待驗證」 |
| **E4** | 兩邊皆無，純結構推論 | **引用時必須明說沒有任何證據** |

每條洞察標上級別。E4 進提案不是問題，**把 E4 講得像 E1 才是問題**。

### Step 4：經濟模型要有自洽性檢查

不要只給總預算。要證明**這個結構在數學上不可能超支**。

寫法：定義一個單位（例如 B = 每個有效新客的獎勵預算 = 其 3 個月 GGR 的 12%），然後證明不管走到哪一階，每人成本恆等於 1B。

同時給出對照基準：目前花多少、上限是多少、這次是幾倍的 step-up、離硬上限還有多遠。

### Step 5：風險寫成 P&L，不是 checklist

風險段落必須有：

- **量化的損失**：作弊帳號造成多少 GGR 損失（含期間、樣本）
- **指名的真實案例**：具體帳號 / 事件當 smoking gun，不要只寫「曾發生過」
- **硬性前置條件**：哪幾條規則是上線前必須完成，不是 nice to have
- **熔斷機制**：累積超過水位時自動切換到人工審查

**分清楚 watchlist 與 verdict**：只有同時疊加多個訊號才算確認，單一訊號只能進觀察名單。未驗證的規則明確標為「方向待驗證，非定案規則」。

**提新規則時，同時交代既有防護的去留**。不要只列新規則就結束 — 對每一條既有機制明確寫「保留 / 調整 / 移除」，並附數據理由與順序安排。

> 例：「保留 referrer activation gate 與 10 筆上限（4,837 人中僅 8 人觸及，上修效益低，排在反農場之後再處理）」

漏掉這段，審核者會問「那原本那些還在嗎」，提案就會被退回。

### Step 6：逐市場參數，不要一組通用數字

市場之間價值可能差 8–15 倍。共用框架，但每個市場算自己的：門檻、有效性標準、獎勵階梯、熔斷水位。

低量體 / 高價值市場要單獨處理（例如排行榜關閉、改推里程碑）。

### Step 7：分階段 + 可檢驗的 exit criteria

每個階段要寫清楚：範圍、預算、以及**用數字定義的過關條件**。

不可接受：「觀察成效後再決定」
可接受：「品質 ≥1.0× 基線 · 成本 ≤15% · ≥60% 團隊達里程碑 1 · 作弊 FTD 占比低於市場基線」

同時列出 **hard dependencies**：哪些系統能力必須先到位，否則整個計畫不能啟動。

#### 7a. Pilot 是實驗，不是「先上線看看」

**光有門檻不夠，還要能判斷「達標了沒」在統計上站不站得住。** 以下六項，pilot 上線前寫進提案：

1. **一句可證偽的假設**：「我們相信 [改動] 對 [對象] 會產生 [結果]，用 [指標] 衡量。」
   一個 pilot 只測一個假設；要測多件事就跑多個 pilot。
2. **對照組**：拿什麼比？沒有對照就只能講前後變化，那會被季節性、行銷檔期、市場波動污染。
   若結構上不能設對照組（例如全市場上線），**明講這是前後比較、不是因果宣稱**。
3. **一個主要指標 + 2-3 個次要指標 + guardrail 指標**。
   guardrail 是抓非預期傷害的（例如「留存沒掉」「客訴沒漲」「作弊佔比沒升」），
   **主要指標達標但 guardrail 破了，算失敗不算成功**。
4. **樣本數與期間**：要偵測多大的效果（MDE）？以目前流量跑多久才夠？
   **期間要涵蓋完整的週間循環**，不要在週三結束一個週末行為差很大的活動。
   算不出來就誠實寫「本 pilot 無法達到統計顯著，結果只能當方向參考」。
5. **事前定義 win / lose / inconclusive 三種結果**，以及各自對應的動作。
   **這一步的目的是防止事後移動球門** —— 你已經踩過同型的坑：
   「出場評估用哪個 margin 口徑必須事前鎖定，同一份 pilot 結果可因事後換口徑得到相反判定」。
6. **門檻敏感度**：把門檻上下各動一檔，結論會不會翻？
   會翻就必須在提案裡標明採用哪個門檻、以及翻轉點在哪
   （實測案例：三種門檻皆為 0 檔達標，但門檻改成 25% 答案就翻）。

> 引用任何既有績效數字當基線時，**一併說明產生它的環境**（期間、市場狀態、活動檔期）。
> 不說環境的數字不可拿來當 pilot 的比較基準。


### Step 8：收尾是 DECISIONS NEEDED

最後一頁不是總結，是**要對方做的決定清單**。每項標注：

- 編號 + 決策內容 + 一句話說明選項
- `Blocking` 或 `Non-blocking`

Non-blocking 的項目要註明「上線後可調」，讓決策者知道現在不用糾結。

底部列出已備妥的交付物與版本號。

### Step 9：GO 後才轉成專案意圖

提案回答「值不值得投資」，不是開發的唯一事實來源，也不等於 `INTENT.md`。

- **GO**：**取得使用者明確核准後**，依你們自己的專案生命週期文件與 INTENT 範本
  （本包不提供，由使用者環境提供；沒有的話就先跟使用者確認要寫哪些欄位）
  把已核准的目標、非目標、成果與硬限制寫進新專案資料夾。之後才判斷是否需要 `SPEC.md`，最後形成 `PLAN.md`。
- **NO-GO／待補證據**：保留提案與決策結果，不建立假的專案意圖，也不往開發計畫跳。

轉換時要保留提案來源與核准日期；不要把未核准的 E3／E4 推論悄悄升格成硬需求。

## 輸出格式

### 頁面標題規則

每頁標題兩層：

```
[ALL CAPS 分類標籤]        ← WHY / THE PROBLEM / FIX 1 / RISK ① / DECISIONS NEEDED
[結論句]                   ← 直接講結論，不是講主題
```

錯：`風險分析`
對：`RISK ①: FARMS` + `One referrer: 452 shell accounts over 5 months, £0.3 avg deposit, unflagged`

### 必備段落順序

新功能提案：
`封面(含證據出處) → WHY(現況與缺口) → 數據洞察→設計決策映射 → 機制 → 計分與獎勵 → 經濟模型 → 風險控制 → UI → 逐市場參數 → 上線計畫 → DECISIONS NEEDED`

成效檢視：
`封面 → Agenda → 競品/現況盤點 → EXECUTIVE SUMMARY(數字化的 N 個結論) → 證據 → 問題 → FIX 1..N → 風險 ①②③ → 行動計畫 → 分階段路線圖 → DECISIONS NEEDED → APPENDIX(資料與方法)`

### 封面必含

資料來源與期間、幣別換算基準、支撐文件與版本號、對象標註（例如 `For Leadership`）。

### 附錄必含

- 用到哪些資料表
- 歸因方法與 key 的組成
- 換算率
- **明確寫出沒有測到什麼**（例如「incrementality 未測，部分自然轉化未扣除」）

## 程式化產出 pptx 時（2026-08-06 實作教訓）

- **本機沒有 LibreOffice**，無法 `soffice --convert-to png` 驗證。改用 **PIL + 系統 Arial
  自寫渲染器**把 pptx 畫成 PNG（作者本機是 `scripts/deck/render.py`，**這支不隨 plugin 發布**，你要自己有一個等價的）。
  這是唯一能抓到顏色錯、字元變方框、元素重疊的方法 —— 這些在 python-pptx 層完全看不出來。
- **Arial 缺字**：`฿`、`⚠`、`✓`、`★` 一律 tofu，`₫` 只有替代字形。
  簡報裡改用 `THB`／`VND`／`CNY` 文字與 `!`／`◆`。
- **表格後面接任何東西都不能寫死 y 座標**。列高會因長儲存格自動撐開，寫死座標會讓最後一列
  被 callout 蓋掉（**而且不會報錯，資料只是靜靜消失**）。讓 `table()` 回傳結束 y，
  後續元素用相對定位。
- **既有簡報的設計系統**：Arial；navy `1E2761`、card `EAF1FB`、pale `CADCFC`、amber `E8A33D`、
  green `0F7B5F`、red `B3261E`、body `5F6368`/`23252B`；13.33×7.5in、邊距 0.60、內容寬 12.10、
  eyebrow y=0.42、標題 y=0.72、頁尾 y=7.08。

## 停止條件（必須問人）

以下情況停下來問，不要自行決定：

- 數字口徑無法確認（期間、狀態、grain、符號方向任一不明）
- 要承諾具體價格、合約條款、付款方式
- 涉及未公開的商業條件或客戶個資
- 需要風控 / 法務簽核的門檻設定
- 決策對象不明，導致深度與語言無法決定

## 驗收標準

提案完成前自檢：

- [ ] 每個數字都過了口徑閘門
- [ ] 每條設計決策都指得出對應的數據，並標了證據級別 E1–E4；E4 已明說沒有證據
- [ ] 經濟模型有自洽性檢查，證明結構上不會超支
- [ ] 風險段有量化損失 + 指名案例 + 硬性前置條件
- [ ] watchlist 與 verdict 已區分；未驗證規則已標注
- [ ] 參數逐市場計算，沒有一組數字套全部
- [ ] 每個階段有數字化的 exit criteria
- [ ] pilot 有：可證偽的假設、對照組（或明說是前後比較）、guardrail 指標、
      樣本數與期間評估、**事前**定義的 win/lose/inconclusive、門檻敏感度
- [ ] 引用的既有績效數字都說明了產生它的環境（期間、市場狀態、活動檔期）
- [ ] 最後一頁是 DECISIONS NEEDED，且標了 Blocking / Non-blocking
- [ ] 附錄寫出了「沒測到什麼」

任何一項打不了勾，就還沒完成。
