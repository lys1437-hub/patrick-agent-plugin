# 一頁式報告

一頁、單檔、點兩下打得開、離線也能開、按 Cmd+P 印得出來。

**這支 Skill 補的不是「會不會做」，是「每次都做對」。** 建立時盤點了 12 份已交付的頁面：
列印規則完整的有 5 份、只有兩條 `display:none` 的有 4 份。同一個人、同一套工具，
差別不在能力，在**沒有一個會擋人的檢查點**。所以本 Skill 的重心是最後那一步。

## 使用時機

- 要人**判斷長相**（版面、流程、對照）或**確認有沒有做到**（成果、驗收）。
- 結果有結構：多個方案要比、多個步驟要看順序、多個數字要並排。
- 對方會**轉寄、離線開、或印出來**帶進會議。

## 不適用

- 三句話講得完的答案。做成一頁只是把資訊藏進版面裡。
- **關鍵口徑還沒定，且不補假設就無法比較。** 先問清楚，不要用看似精確的數字填空。
- 需要即時更新或連資料庫的儀表板——那是應用程式，不是一頁報告。
- 對方要的是可編輯的原始檔（簡報、試算表）。

## 未定案時：只能做決策地圖

「最後選哪個」未定，不代表完全不能排版；但頁面必須是**決策地圖**，不能偽裝成成果報告：

- 標題或第一屏明寫「未定案」「討論版」或同等清楚的狀態。
- 不宣布贏家、不給單一推薦；只呈現已知事實、選項差異、條件分支與待拍板項目。
- 只能使用使用者提供或已驗證的事實。未確認的用量、期間、價格、工時、效益等，不得默默補入計算。
- 若缺少的口徑會決定排序或精確數字，先問；若仍要先做，只能做**不新增假設**的討論地圖，並把空缺列為待決變數。
- 第一屏的「所以呢」可以是後設結論，例如「目前無法排序；一天用量與預算上限會翻轉選擇」。不能把條件式判斷排成已定案決策。

## 第一件事：先問這頁會被怎麼使用

**不要跳過。** 螢幕與列印的硬性要求不同，事後補比一開始寫貴得多。

| 用途 | 硬性要求 |
| :-- | :-- |
| 螢幕閱讀 | 三態主題（見下）；寬表格自己橫向捲動，頁面本體不左右捲 |
| **會被印出來** | `@page` 定紙張與邊界；`print-color-adjust: exact`；每張卡 `break-inside: avoid` |
| 兩者都要 | 上面兩組都做，並在列印時隱藏切換鈕等螢幕專用元件 |

沒有色底、沒有卡片的純文字頁可以不做列印規則；**只要有色塊就要做**——
沒有 `print-color-adjust` 時，chip、進度條、狀態底色在紙上會整片消失，
讀的人看到的是一堆沒有顏色的標籤，而顏色本來就是那頁的資訊。

## 開始寫之前

**先整份複製 [references/skeleton.html](references/skeleton.html)，再改內容。**
它已經含好色票、三態主題、列印規則與四個段落骨架，本身通過檢查器。
從空白開始寫 CSS 的代價不是慢，是每頁的 token 命名都不一樣，下一頁又得重來。

## 內容結構（順序有意義）

1. **結論先行。** 第一屏就要能回答「所以呢」。未定案決策地圖則回答「目前能確定什麼、還缺什麼」。不要用背景鋪陳開場。
   **標題寫結論，不要寫主題**——「UI 一致性體檢」是主題，「13 個灰，6 個肉眼分不出來」是結論。
   主題式標題讓人非讀完才知道要不要在意。
2. **證據。** 數字旁邊寫出處與口徑；比較用同一張表，不要分散在各段。
3. **我自己搞錯的。** 只在回報「自己做的工作」時放：列出過程中被推翻的判斷。
   這一段是頁面可信度的來源——**沒有錯誤的成果報告，讀的人只會假設你沒查。**
4. **還沒做完 · 需要拍板。** 明確標出等誰決定什麼。沒有這段，讀的人不知道要回你什麼。

## 視覺規則

### 浮動目錄目前不納入

2026-09-08 後續盤點作者本機草稿目錄的 13 份本機 HTML：0 份使用 anchor TOC；最長頁面雖有
11 個二級標題，但主要用途仍是列印小卡、第一屏結論與單頁決策，不是反覆跨章查找。
這是本機快照，不是隨 Skill 散布的可重現基準；它只能支持「目前不預設加入」，不能證明永遠無需求。
目前沒有真實使用證據能抵銷浮動元件在窄螢幕遮內容、列印時另做隱藏規則、以及維護 anchor 的成本。

因此預設不做浮動 TOC，也不引入 `diagram-design` 或其他外部依賴。只有同時符合以下條件才重評：

- 明確是螢幕閱讀，不以列印為主。
- 至少 6 個可獨立查找的章節，且成品高度超過 4 個常用視窗高度。
- 先試頁首 inline TOC；至少一次實際閱讀觀察到「需要回到先前章節但定位困難」，才做只在寬螢幕
  顯示、列印時隱藏的 sticky／floating 版本。沒有觀察紀錄就維持 inline 或不做。

**語意色票用固定命名，不要每頁重新發明。** 混用同義名（`--ok` 一頁、`--good` 另一頁）
的代價不是難看，是**頁面之間無法沿用**，每次都得從頭寫 CSS：

```
--bg --card --ink --muted --rule          結構
--accent --accent-soft                    主色／淡底
--good --good-soft                        通過、達標
--warn --warn-soft                        注意、待確認
--bad  --bad-soft                         失敗、風險
```

**三態主題**（缺一態就會有人看到壞掉的版本）：

```css
:root { /* 淺色：完整定義所有 token */ }

@media (prefers-color-scheme: dark) {
  :root:not([data-theme="light"]) { /* 跟隨系統 */ }
}

:root[data-theme="dark"] { /* 手動切換要贏過系統，兩個方向都要 */ }
```

任何顏色都不要只定義在 media query 或 `[data-theme]` 區塊裡。

**零外部依賴。** 不引 CDN、不引字型檔、不引外部圖片；圖片一律 data URI。
理由不是潔癖：交付物會被轉寄、會在沒網路的會議室打開、會被存進附件。
**外連在那些場合不是變慢，是不見。**

中文要指定字型 stack（`"PingFang TC","Noto Sans TC","Microsoft JhengHei"` 等），
否則換一台機器就掉字型。

## 署名

頁面只帶**這份工作自己的**署名與連結。產生器、範本、課程的名字與網址不要留在交付物上——
它會跟著頁面寄給客戶、面試官、主管，而他們看到的是你的名字底下掛著別人的連結。

## 完成前必跑

```
python3 scripts/check_page.py <檔案> [--print]
```

退出碼非 0 就是還沒完成。它檢查的每一條，都對應一個真實發生過的交付缺陷。

**不要用「我檢查過了」代替實跑。** 這支 Skill 存在的理由就是人（與 AI）會漏掉這些。

## 停止條件

- 未定案，且關鍵口徑不足以在不新增假設下完成使用者要求的比較或計算 → 停下來先問。
- 未定案，但可用現有事實做決策地圖 → 明標未定案，只呈現條件與待決變數，不替使用者定案。
- 數字沒有出處 → 停下來問，不要在頁面上寫一個看起來很確定的數字。
- 需要的是即時資料 → 說明一頁報告是快照，問他要不要改成定期產出。
