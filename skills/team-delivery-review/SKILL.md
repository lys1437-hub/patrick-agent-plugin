# 團隊交付驗收

判斷別人宣稱完成的工作是否真的可接手。輸出是驗收結論，不是修復成果。

## 邊界

- 自己剛完成的工作，改用 `report-and-verification`。
- 對方尚未宣稱完成時，只能報告進度，不下完成判定。
- 先保存發現與證據，不修改交付物；修正需要另一項明確授權。
- 交接文件、commit message、口頭保證都是線索，不是完成證據。

## 1. 鎖定範圍與時間

開始前記錄：本次承諾範圍、任務開始時間、完成宣告時間及驗收時間。

檔案時間晚於開始時間，只能證明期間曾改動。完成宣告後又修改的產物，宣告前的 pass、截圖或 log
不能自動沿用；必須重跑或明確標成舊證據。找不到可靠時間分界時，保留「時間歸屬不明」盲區，
不以 mtime 猜測。

## 2. 宣告觀測視角

| 視角 | 能回答什麼 | 常見盲區 |
| :-- | :-- | :-- |
| 工作區 | 未提交、未追蹤內容是否存在 | 只有該機器看得到 |
| 本機 commit | 哪些內容已進版本歷史 | 可能尚未推送 |
| 遠端 repo | 團隊實際能取得什麼 | 不代表已部署 |
| runtime／部署環境 | 使用者實際拿到哪一版 | 不一定能反推 source commit |

無法觀察的層級寫 `unavailable`，不要假設與上一層一致。

## 3. 查產物，不接受自述

按交付種類取得直接證據：

- 檔案：存在、內容、大小、可開啟性與必要欄位；
- 程式：相關 diff、commit、測試與實際輸出；
- 數字：來源、口徑與可重算結果；
- 發布：遠端版本、部署識別與實際頁面或服務行為。

每項證據都標出產生時間、對應版本與視角。舊版證據不能替新版背書。

## 4. 跨產物對讀

同一狀態、數字、清單或版本若出現在多處，先對齊定義再並排比對。矛盾未裁決時，不選最新檔案、
最漂亮的文件或最有把握的敘述當真相。尤其檢查 handoff 與 repo、驗證 log 與產物版本、remote 與
runtime，以及宣告後修改是否已有新證據。

## 輸出契約

```markdown
## 驗收結論
- 交付範圍：完成／部分完成／未完成／無法判定
- 證據充分度：充分／有限／不足
- 準備度：可接手／可 demo 但有限制／可發布／不可進下一步／無法判定
- 觀測視角：workspace／local commit／remote／runtime（逐項標 available 或 unavailable）

## 直接證據
- [實際看過的路徑、commit、指令或輸出，以及時間與版本]

## 缺口與矛盾
- [缺少的交付、失效的舊證據、跨檔或跨環境矛盾]

## 盲區與翻案條件
- [目前看不到什麼；補到什麼證據會改變結論]
```

「可 demo」不等於「可發布」；「code 在遠端」不等於「runtime 已更新」。三個結論必須分開。

## 停止條件

產出驗收結論後停止。不要順手修字、補文件、推送、部署或改狀態；保存證據後等待新的修正授權。

## 驗收標準

- 範圍、開始時間、完成宣告時間都有記錄或標明不可得。
- 四個視角逐層陳述，沒有把 remote 當 runtime。
- 完成、證據與準備度分開判斷。
- 宣告後修改會使舊證據失效。
- 結論引用直接證據並列出盲區。
- 沒有改動被驗收的交付物。
