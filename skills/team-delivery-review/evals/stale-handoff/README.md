# Case: stale-handoff

**這是合成案例，不對應任何真實專案。** 領域（健身房候補名單）刻意選在
本 repo 與作者機器上都不存在的範圍。

## 🔴 為什麼要合成：前一版洩漏到真實環境

2026-09-04 手動跑第一版時，**四條規則全部命中，但那次測試無效**。

第一版是把一個真實的外部交付物改短檔名當「合成案例」。
在作者的機器上跑，模型直接去查了真實 repo，回答裡出現 prompt 裡根本沒有的東西
（真實的決策編號、參考站的人名、未提及的檔案、分支領先落後數）。

**它答對了，但不是靠 prompt 答的。** 同一份 prompt 拿到沒有那個專案的機器上，
結果會完全不同 —— 而那正是這包 skill 分發出去之後的情況。

**「我以為它自包含」與「它真的自包含」，在本機跑起來長得一樣。**
唯一能分辨的方法，是換一個那台機器上不可能有的領域。

## 測什麼

`team-delivery-review` 的四條規則，各對應一個刻意埋的陷阱：

| 規則 | 陷阱 |
| :-- | :-- |
| 1 先宣告視角 | 產物只在提交者的工作區，三個視角答案不同 |
| 2 先切時間分界再看檔案 | 三份交接文件的 mtime **早於任務開始時間** —— 看起來剛更新過 |
| 3 共用數字跨檔對讀 | 頁面 `30`／`45 分`／`扣 2 點` vs 已驗證的 `12`／`扣 1 點`，且無文件說明哪個是新基準 |
| 4 文件自述不算證據 | `HANDOFF.md` 寫 `in_progress` 且指向**舊檔**（沒有 `_v2`） |

刻意讓「看起來完成」與「實際完成」相反。抓到版控狀態與證據缺漏是 baseline
就會的，**這裡評的是四條規則各自對應的那個發現**。

## 怎麼跑（`claude plugin eval` 至今仍是 early access）

開一個**全新對話**，把 `prompt.md` 整份貼上。不要貼 grader、不要說這是測試、
不要先叫 skill —— 路由本身是被測的一部分。第一則完整回覆拿去對 `graders/`。

## 已知限制

- 1 個 case，四條規則各測一次，**不涵蓋停止條件之外的邊界**
- grader 是散文式判準，需要人或 LLM judge，沒有可機械驗證的斷言
- **合成案例換不掉一件事**：它仍在作者的 repo 裡。跑之前確認那台機器上
  沒有健身房／候補名單相關專案（`grep -rli "候補\|waitlist"`），
  有的話這個 case 就跟前一版一樣廢掉了。
