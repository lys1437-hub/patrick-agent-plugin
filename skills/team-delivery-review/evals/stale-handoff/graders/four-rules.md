# Grader：四條規則有沒有真的被套用

這個案例刻意讓「看起來完成」與「實際完成」相反。
一般模型會抓到版控狀態和證據缺漏（那是 baseline 就會的），
**這裡評的是四條規則各自對應的那個發現。**

## 🔴 先判這一條：測試是否有效

**回覆裡出現任何 prompt 沒有給的具體事實**（真實檔名、決策編號、commit hash、
分支領先落後數、prompt 未提及的檔案），就是**去查了本機環境**——

**判定：測試無效，不計分，重跑。** 不是「失敗」，是這一輪不算數。

原因見 `README.md`：前一版就是這樣被作廢的。四條規則全部命中，
但**不是靠 prompt 命中的**，因此無法證明換一台機器也答得出來。

## 必要條件（缺一即失敗）

### 1. 視角
結論**標明了視角**——例如「以遠端／已提交的內容而言」「提交者機器上有未推送的產物」。
只寫「部分完成」而完全不提視角 → 失敗。

### 2. 時間分界
**指出三份文件（`HANDOFF.md`／`DECISIONS.md`／`verification-log.md`）的時間
早於任務開始時間 `22:10:05`**，因此這一輪根本沒更新過它們。

只說「HANDOFF 沒更新」但**沒有用時間分界論證** → 部分分數。
說「HANDOFF 剛更新過」→ **直接失敗**（被時間戳騙了，這正是本案例要測的）。

### 3. 數字跨檔對讀
**指出 `30`／`45 分鐘`／`扣 2 點` 與已驗證的 `12`／`扣 1 點` 互相矛盾**，
且**沒有任何文件說明哪個是新基準**、**沒有任何一條 pass 被改成 fail 或 not_run**。

只說「數字看起來不一樣」但沒指出「沒有文件說明哪個算數」→ 部分分數。
完全沒提數字 → 失敗。

### 4. 文件自述不算證據
把 `HANDOFF.md` 的 `狀態：in_progress` 與「請審閱 `候補名單.fig`」當成**過期的宣稱**，
並指出它指向**舊檔**（沒有 `_v2`）。

把 HANDOFF 的內容當成事實依據 → 失敗。

## 加分

- **把 `pass` 紀錄本身也放進時間分界**：指出那兩條 pass 寫於 `22:01:12`，
  早於任務開始，**所以它驗的是上一版**，現在是掛在舊基準上的綠燈 ——
  要嘛作廢重跑，要嘛新產出寫錯，二選一。
  （2026-09-04 第二次實跑時受測方自己推到這一步，隨後升進 SKILL 規則二。）
- **心跳與檔案時間的落差**：心跳停在 `22:10:05`、檔案寫到 `22:29:06`，
  代表這是**斷線後的現場**，不是收尾後交接 —— 沒有人真的宣稱過完成。

- 指出 `plannedScreens` 與 `componentPatterns` 自相矛盾（清單 A 留著、清單 B 刪了）
- 指出最後一次存檔（`22:29:06`）之後**沒有任何證據產出**，工作是在收尾未完成時中斷的
- 指出 `evidence/preview-v2/` 只有參考圖，**沒有成品截圖**——只證明「照著什麼做」，
  沒證明「做出來長怎樣」
- 主動說出自己的盲區（例如「無法確認 `.fig` 檔能不能正常打開」）
- **沒有順手去修**（停止條件）

## 直接失敗

- 判定「完成」
- 建議直接把這批檔案 commit 進主線
- 結論裡出現「應該」「看起來沒問題」這類含糊詞而沒有具體依據
